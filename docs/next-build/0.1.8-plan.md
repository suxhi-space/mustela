# 0.1.8: plan

Started after 0.1.7-build2. Each item has what it means, what's possible for free, and what's needed from you.

## 1. iPhone and iPad (iOS)

Tauri builds for iOS from the same code. Building needs a Mac with Xcode (you have one).

Ways to get it to people:

| Way | Cost | Catch |
|---|---|---|
| **AltStore / SideStore** (sideloading with the person's own Apple ID) | Free | With a free Apple ID the app stops opening after **7 days** until it's refreshed (AltStore/SideStore can do that in the background over Wi-Fi). At most 3 sideloaded apps per Apple ID. |
| **TestFlight** | Apple Developer Program, $99/year | Up to 10,000 testers by link; each build lasts 90 days. Easiest for people. |
| **AltStore PAL** (EU only, an alternative app store) | $99/year + Apple's review of the app | EU only. |
| **App Store** | $99/year | Full review; Stoat-style apps can get through but it takes work. |

Plan: start with an **IPA for AltStore/SideStore** (free). The build script gets an "iOS" option that makes the .ipa; a page in the README explains sideloading.

What needs doing in the app:
- [ ] iOS project (Tauri `ios init`), icons, the build script option
- [ ] The native parts written for iOS too (Android has them in Kotlin): sign-in in the iOS Keychain, calls and microphone in the background, picture-in-picture, photos in the + card, share/save in the viewer
- [ ] Check every screen at iPhone sizes (notch and home bar spacing, keyboard)
- [ ] Screen sharing from iPhone is a separate, harder job (Apple's broadcast extension); likely later

**Limit to know:** iOS doesn't let apps check for messages in the background like Mustela does on Android. Notifications while Mustela is closed need Apple's push service, which needs the paid developer account (see 2). Without it, notifications only arrive while the app is open or was just used.

## 2. Better notifications on phones (real push)

Today Android checks for new messages in the background (about every minute with the screen on, about every 15 minutes with it off), so they can come late or in bursts. Real push means Stoat's server sends a ping the moment a message arrives.

**How it works:** Mustela registers a **Web Push** address with Stoat once (Stoat's `POST /push/subscribe`, with the user's own session, sent only to Stoat). From then on **Stoat itself pushes** each message to that address. The message is encrypted on Stoat's side with keys made on the phone, so nothing in between can read it, only Mustela. No live connection to Stoat, so you don't show as online.

**How the push reaches the phone (the choice is about battery and extra apps):**

| Route | Extra app? | Battery | Server of ours? |
|---|---|---|---|
| **Through Google's push service (Firebase), built into Mustela**: the main route | No | Low (Google's one shared connection does the waiting) | A tiny relay that turns Stoat's Web Push into a Firebase message. It **stores nothing**, sees only encrypted data and never a Stoat token |
| ntfy app (UnifiedPush), from Google Play | Yes | Low | No |
| ntfy app from F-Droid (no Google) | Yes | Higher (its own connection) | No |
| Mustela holding its own connection | No | Higher, plus a permanent notification | No. **Dropped because of battery** |

**The relay, kept as small as possible:**
- Stateless: the address Mustela gives Stoat already says which phone it's for (it carries the phone's Firebase ID), so the relay has no database and keeps nothing.
- Fits a free host (e.g. a Cloudflare Worker's free tier).
- It holds Mustela's Firebase sending key. That key is a secret: it lives on the relay only, never in the repo or the zips.
- What it can see: that *some* phone got *a* push and when, never who sent it or what it says.
- If the relay is down, notifications fall back to today's background check.
- Later the same relay can also send to iPhones through Apple's service (needs the $99 account).

**Plan:**
- [ ] **Step 1, a test before building anything:** register one subscription with api.stoat.chat from Mustela (does Stoat accept a non-official app? does it allow push addresses that aren't Google's or Mozilla's?) and look at what a push contains (the message text and author, or just "something new"?). Read Stoat's push server code for how it behaves (study only, no copying).
- [ ] Android: Firebase in Mustela (the build script adds Google's setup file), the subscribe call, decrypting pushes (standard Web Push encryption), then the usual chat notification. Mustela's own mute and "mentions only" rules are applied after decrypting.
- [ ] The relay (Cloudflare Worker or similar), stateless, with the deploy steps in the README
- [ ] Settings > Notifications: "Instant (Google)", "ntfy" (for phones without Google, if a UnifiedPush app is installed), or "Battery saver" (today's check)
- [ ] Keep today's background check as the fallback, and less often (for example every 30 minutes) to clear notifications for chats you read elsewhere, since a push doesn't say when something was read
- [ ] Check that the official UnifiedPush/Firebase helper libraries are still maintained before using them; if not, use Firebase's own library directly (same design)

**Things to know:**
- Phones without Google services (some Huawei phones, de-Googled ROMs) can't use the Google route; they get ntfy or the background check.
- If Stoat's server only pushes to Google or Mozilla addresses, the relay plan needs rethinking. That's why step 1 comes first.
- **iPhone:** Apple's push service only (the $99/year account), through the same relay. Without the account, iPhone notifications only arrive while the app is open or was just used.

## 3. Signing the apps

Yes, this happens during the build, so the build script handles it: it asks once where your certificate is (or reads it from the environment) and signs; with nothing set up it builds unsigned like now.

| System | What it needs | Cost |
|---|---|---|
| **Android** | Already signed with your own key | Done |
| **Windows** | A code-signing certificate. Free for open-source projects through **SignPath Foundation** (they sign for you, from GitHub builds). Otherwise Azure Trusted Signing (about $10/month) or a certificate (~$200+/year) | Free with SignPath (needs approval) |
| **macOS** | Apple Developer ID + notarization | $99/year (the same account as TestFlight) |
| **Linux** | Nothing required | Free |

Plus one free improvement for everyone:
- [ ] **Signed updates:** Mustela's own update key (free). The build script signs each release file, the app checks the signature before installing (on top of GitHub's checksum). Then even someone who got into the GitHub account couldn't push a fake update.
- [ ] Build script: Windows signing step (SignPath or a certificate), macOS signing + notarization step, both skipped when not set up
- [ ] Without paid signing: README notes for "Windows protected your PC" and macOS "unidentified developer"

## 5. Windows call pop-out (the 0.1.7-build2 fix didn't work)

What you see on Windows: the pop-out has the Windows frame, an **address bar**, "about:blank" as its title and a globe icon in the taskbar.

Why: on Windows the pop-out is WebView2's own pop-up window (Mac and Linux use a proper Mustela window). The build2 fix looked for that window by the title "Mustela call" to take its frame off, but Windows keeps the title "about:blank", so it never found it. And the address bar is drawn inside WebView2's pop-up, so taking the frame off could never have removed it anyway.

The real fix: make the pop-out a proper Mustela window on Windows too, the way Mac and Linux already do (Tauri's own way). That froze both windows when it was tried in 0.1.5, so it needs debugging on a Windows PC:
- [ ] A debug build that logs each step of opening the pop-out, to see where it freezes
- [ ] Try the likely causes (making the window inside the request vs. just after it; sharing the main window's WebView2 setup)
- [ ] Then: Mustela's title bar (following the Title bar setting), "Mustela call" title, Mustela's icon in the taskbar, no address bar
- [ ] If Tauri's way can't work on Windows: the fallback is taking out the build2 frame code so it doesn't run for nothing

Needs a few test builds on your Windows machine.

## 6. Linux AppImage for older systems

The AppImage is built on Ubuntu 24.04, so it needs a fairly new Linux (roughly 2024 or newer: Ubuntu 24.04, Fedora 40, current Arch). It doesn't start on Ubuntu 22.04, Debian 12, Linux Mint 21 and similar, because those have an older system library (glibc) than the one it was built with.

Why it's built on 24.04: Linux screen sharing needs PipeWire 1.0, and Ubuntu 22.04 only has 0.3.

- [ ] Build the AppImage on an older base (Ubuntu 22.04) with a newer PipeWire installed just for building (PipeWire's own packages, or built from source in the build step)
- [ ] Or keep screen sharing working with the older PipeWire too, if the library allows it
- [ ] Test the result on Ubuntu 22.04 / Debian 12 and on a new distro
- [ ] README: say which Linux versions the AppImage runs on

## 7. Tidying the code (no duplicate code)

Today the styles are about 330 KB (296 KB desktop/shared + 37 KB mobile) and the main app code about 880 KB. Several things are built more than once:
- **Hold cards / bottom sheets:** each one (message, user, server, channel, emoji, the + card...) has its own copy of the card styles. One shared card style and one shared sheet component.
- **Tabs:** Friends, search, the search panel, profiles, reactions, GIFs, the emoji/GIF card and the screen picker each style their own tab row (8 different ones). One tab style and one tab component, with the swipe built in. (This also settles the old "pills or segmented" question: one look everywhere.)
- **Menus, buttons and dialogs:** the same consistency pass (left over from 0.1.7).

- [ ] Go through styles.css and mobile.css: merge repeated rules, remove unused ones
- [ ] Shared Sheet, Tabs and Card components; move each screen onto them
- [ ] Split the main code so rarely used parts load only when opened (the 880 KB main file)
- [ ] Sweep at all four sizes after each step, so nothing looks different by accident

To be honest about the gain: this will make the app faster to open and easier to change, and the web part smaller. But most of the installer's size is the app shell and call engine, not this code, so the download won't shrink much.
