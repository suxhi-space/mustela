## 2. Better notifications on phones (real push)

Today Android checks for new messages in the background (about every minute with the screen on, about every 15 minutes with it off), so they can come late or in bursts. Real push means Stoat's server sends a ping the moment a message arrives.

**How it works:** Mustela registers a **Web Push** address with Stoat once (Stoat's `POST /push/subscribe`, with the user's own session, sent only to Stoat). From then on **Stoat itself pushes** each message to that address. The message is encrypted on Stoat's side with keys made on the phone, so nothing in between can read it, only Mustela. No live connection to Stoat, so you don't show as online.

**How the push reaches the phone (the choice is about battery and extra apps):**

| Route | Extra app? | Battery | Server of ours? |
|---|---|---|---|
| **Through Google's push service (Firebase), built into Mustela**: the main route | No | Low (Google's one shared connection does the waiting) | A tiny relay that turns Stoat's Web Push into a Firebase message. It **stores nothing**, sees only encrypted data and never a Stoat token |
| ntfy app (UnifiedPush), from Google Play | Yes | Low | No |
| ntfy app from F-Droid (no Google) | Yes | Higher (its own connection) | No |
| Mustela holding its own connection | No | Higher, plus a permanent notification | No. **Dropped because of battery** |

**The relay, kept as small as possible:**
- Stateless: the address Mustela gives Stoat already says which phone it's for (it carries the phone's Firebase ID), so the relay has no database and keeps nothing.
- Fits a free host (e.g. a Cloudflare Worker's free tier).
- It holds Mustela's Firebase sending key. That key is a secret: it lives on the relay only, never in the repo or the zips.
- What it can see: that *some* phone got *a* push and when, never who sent it or what it says.
- If the relay is down, notifications fall back to today's background check.
- Later the same relay can also send to iPhones through Apple's service (needs the $99 account).

**Plan:**
- [ ] **Step 1, a test before building anything:** register one subscription with api.stoat.chat from Mustela (does Stoat accept a non-official app? does it allow push addresses that aren't Google's or Mozilla's?) and look at what a push contains (the message text and author, or just "something new"?). Read Stoat's push server code for how it behaves (study only, no copying).
- [ ] Android: Firebase in Mustela (the build script adds Google's setup file), the subscribe call, decrypting pushes (standard Web Push encryption), then the usual chat notification. Mustela's own mute and "mentions only" rules are applied after decrypting.
- [ ] The relay (Cloudflare Worker or similar), stateless, with the deploy steps in the README
- [ ] Settings > Notifications: "Instant (Google)", "ntfy" (for phones without Google, if a UnifiedPush app is installed), or "Battery saver" (today's check)
- [ ] Keep today's background check as the fallback, and less often (for example every 30 minutes) to clear notifications for chats you read elsewhere, since a push doesn't say when something was read
- [ ] Check that the official UnifiedPush/Firebase helper libraries are still maintained before using them; if not, use Firebase's own library directly (same design)

**Things to know:**
- Phones without Google services (some Huawei phones, de-Googled ROMs) can't use the Google route; they get ntfy or the background check.
- If Stoat's server only pushes to Google or Mozilla addresses, the relay plan needs rethinking. That's why step 1 comes first.
- **iPhone:** Apple's push service only (the $99/year account), through the same relay. Without the account, iPhone notifications only arrive while the app is open or was just used.

## 3. Flatpak (Flathub)

**Covers older Linux too** (moved here from build1): building the AppImage on Ubuntu 22.04 doesn't work, because the screen-capture library (xcap) needs PipeWire 1.0, which 22.04 doesn't have, and the only ready-made newer PipeWire for 22.04 is an abandoned third-party archive. A Flatpak brings its own up-to-date libraries, so it runs on Mint 21, Ubuntu 22.04, Debian 12 and similar whatever their age. The AppImage, .deb and .rpm stay "2024 and newer" (the README says so).

Many Mint, Fedora and Steam Deck users install apps from Flathub (built into Mint's Software Manager, Fedora's Software, KDE Discover). A Flatpak runs on almost any distro whatever its age, and updates come through the app store.

# Ideas for later (not promised for 0.1.8)

### In-game overlay (optional, off by default)

Discord is bringing its overlay to Linux and macOS (it used to be Windows only): who's in your call and who's talking, and message notifications, drawn over the game. Their demo video (Fedora 44, KDE Plasma on Wayland, playing WoW) shows:
- the voice call as a small list in a corner: avatar, name, and tags like "LIVE" for who's streaming
- **someone's stream in a small window over the game** (a friend playing Slay the Spire 2), which can be moved and resized
- an interactive mode where the overlay's windows can be rearranged, then it goes back to click-through

How Mustela would do it, safely:
- **A see-through window that floats over the game**, not code injected into the game. Injecting into games is how the old Discord overlay worked, and it can get people flagged by anti-cheat (Valorant, Fortnite and others). A floating window can't.
- Clicks go through it to the game; a hotkey makes it clickable (to mute, deafen, reply).
- Mustela already spots running games (for "Playing…"), so it can appear only while a game is running.

Limits to know:
- Games in **exclusive full screen** (mostly older Windows games) draw over everything, so the overlay won't show there; borderless/windowed full screen works. Most modern games default to borderless.
- **Linux on Wayland:** KDE and most other desktops allow an overlay window; **GNOME doesn't** let apps float windows over others in the same way, so it may not show there. X11 works.

Settings (Settings > Overlay):
- [ ] Off by default; turn it on
- [ ] Corner of the screen, size, see-through amount
- [ ] What it shows: voice call (everyone / only who's talking), message notifications, both
- [ ] Watch a stream from the call in a small window over the game (move and resize it in interactive mode; Mustela's mini call view can be the starting point)
- [ ] Hotkey to make it clickable
- [ ] Only while a game is running / always while in a call
- [ ] Turn it off for certain games

### A Rust-drawn desktop app (GPUI), like Discord's "Phoenix"

Discord's new desktop app draws its interface with GPUI (Rust, from the Zed editor's makers; gpui-kit bundles it with
ready-made components) instead of a web engine, so it looks and works the same on every system without Chromium; its
phones use native views over a shared Rust core. Mustela uses each system's own web engine (no Chromium, by choice),
which is why some fixes are per-system.

What switching would mean: rebuilding every screen in Rust (all of today's interface is web code), a Rust Stoat client
in place of stoat.js, and phones either staying on the current app or getting native interfaces of their own (GPUI is
desktop only). Embeds like YouTube would still need a system web view, as in Discord's app.

Not for 0.1.8-build2, 0.1.9 or 1.0.0 (1.0.0 should be today's app, finished). If wanted, start with a small side

If it goes ahead ("Mustela 2"), the shape Discord uses: a Cargo workspace with
